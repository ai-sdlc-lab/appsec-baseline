# Security requirements

Owner: AppSec (this repository). App repositories and their agents read this file at a pinned commit; they never edit it.

Each requirement has:
- **Applies when**: one or more triggers from the fixed list below. A requirement is applicable to a change if any of its triggers is true for that change.
- **ASVS**: OWASP ASVS 5.0 requirement or section IDs (checked against `OWASP/ASVS` `5.0/en`, 2026-10-21). `—` where ASVS has no equivalent; the other source is named.
- **Evidence**: what must exist for the auditor to mark the requirement *covered*: a spec section, a named test, or a scanner rule.

## Triggers

| Trigger | True when the change… |
|---|---|
| `INPUT` | accepts data from users or other external sources (body, query, path, headers, files, metadata) |
| `ENDPOINT` | adds or changes an HTTP endpoint or a served page |
| `WRITE` | lets a caller create, change or delete data |
| `FILE` | accepts, stores, transforms or serves files |
| `AUTHN` | adds or changes how callers are identified |
| `AUTHZ` | exposes data or actions that differ by caller, owner or role |
| `DATA` | handles personal or sensitive data |
| `LOG` | adds or changes logging |
| `SECRET` | uses credentials, keys or tokens |
| `DEP` | adds or updates a dependency, base image or tool |
| `IAC` | changes infrastructure or IAM |
| `CI` | changes CI/CD workflows or their permissions |
| `AI` | adds or changes LLM or agent behaviour, prompts or tools |

## Input and output

### SR-001 Server-side input validation
All external input is validated on the server against an allow list: type, length, range, format and allowed values. Client-side checks are only for usability.
- Applies when: `INPUT`
- ASVS: 2.2.1, 2.2.2
- Evidence: spec *Inputs* table with a limit for every field; tests `test_*_rejects_*` for each rejected class

### SR-002 Injection-safe interfaces
Queries, OS commands, object-storage keys and file paths are never built by concatenating untrusted data; parameterised or typed APIs are used.
- Applies when: `INPUT`
- ASVS: 1.2.4, 1.2.5
- Evidence: Semgrep CE clean on injection rules; injection-input reviewer has no open findings

### SR-003 Context-correct output encoding
Untrusted data is encoded for the output context. The web frontend renders untrusted data only through text APIs (`textContent`, attribute setters), never `innerHTML` or equivalent.
- Applies when: `INPUT`, `ENDPOINT`
- ASVS: 1.2.1, 1.2.3
- Evidence: Semgrep CE clean on DOM-XSS rules; reviewer check

### SR-004 Response headers
Every response has a correct `Content-Type` and `X-Content-Type-Options: nosniff`; HTML responses carry a `Content-Security-Policy` including `frame-ancestors`.
- Applies when: `ENDPOINT`
- ASVS: 4.1.1, 3.4.3, 3.4.4, 3.4.6
- Evidence: test `test_security_headers`; ZAP baseline has no header alerts

### SR-005 Safe errors
Errors return a generic message without stack traces or internal details, and the application fails closed.
- Applies when: `ENDPOINT`
- ASVS: 16.5.1, 16.5.3
- Evidence: test that forces an internal error and asserts a generic body

### SR-006 Abuse and resource limits
Endpoints that write data or consume significant resources enforce request-size and rate or concurrency limits so one caller cannot exhaust the service, its storage or its budget.
- Applies when: `WRITE`, `FILE`
- ASVS: 2.4.1, 15.2.2
- Evidence: spec *Limits* section; test for the size limit; infra setting for concurrency or rate

## File handling

### SR-007 Upload size limit
The maximum upload size is enforced on the server before the file is fully processed or stored.
- Applies when: `FILE`
- ASVS: 5.2.1
- Evidence: spec states the maximum size; test `test_upload_rejects_oversize`

### SR-008 Upload type allow list
Uploads are accepted only if both the extension and the detected content (magic bytes) match an allow list (for images: JPEG, PNG, WebP).
- Applies when: `FILE`
- ASVS: 5.2.2
- Evidence: tests for a wrong extension and for a renamed non-image

### SR-009 Image dimension limit
Images larger than the maximum pixel dimensions are rejected before decoding them fully (pixel-flood protection).
- Applies when: `FILE` (images)
- ASVS: 5.2.6
- Evidence: test `test_upload_rejects_pixel_flood`

### SR-010 Server-generated storage names
Storage keys and paths are generated by the server. User-supplied filenames are never used in paths or keys and are not reflected unencoded.
- Applies when: `FILE`
- ASVS: 5.3.2, 5.4.1
- Evidence: test that a filename such as `../../x` does not appear in the stored key

### SR-011 Uploaded files are inert
Uploaded files are never executed and are served only with a fixed safe `Content-Type`, `nosniff` and from storage, not from the application origin as active content.
- Applies when: `FILE`
- ASVS: 5.3.1, 3.4.4
- Evidence: spec *Serving* section; test of the served headers

### SR-012 Malware scanning before serving
Files from untrusted sources are scanned before they become visible to other users; unscanned or infected files stay quarantined.
- Applies when: `FILE`
- ASVS: 5.4.3
- Evidence: spec *Quarantine* flow; test that an unscanned file is not listed

### SR-013 Per-user upload quota
A per-user limit on the number and total size of uploads is enforced.
- Applies when: `FILE`, `WRITE`
- ASVS: 5.2.4
- Evidence: spec quota values; test `test_upload_quota`

## Authentication and authorisation

### SR-014 Authenticated writes through a managed identity provider
Functions that write data or are specific to a user require authentication through a managed identity provider. The application does not store passwords itself and protects login against brute force as the provider allows.
- Applies when: `AUTHN`, `WRITE`
- ASVS: V6.8 (section), 6.3.1
- Evidence: spec *Authentication* section naming the provider; test that unauthenticated writes return 401

### SR-015 Server-side authorisation, deny by default
Function-level and object-level authorisation are enforced on the server on every request, denying by default. Ownership is checked on every object access.
- Applies when: `AUTHZ`, `WRITE`
- ASVS: 8.2.1, 8.2.2, 8.3.1
- Evidence: authorisation matrix in the spec; tests per role including cross-user access (`test_*_other_user_forbidden`); authn-authz reviewer clean

### SR-016 No default accounts, MFA for administration
There are no default or shared accounts, and administrative access requires MFA.
- Applies when: `AUTHN`
- ASVS: 6.3.2, 6.3.3
- Evidence: spec statement; identity-provider configuration in IaC

## Logging and data

### SR-017 Security event logging
Authentication results, authorisation failures and rejected input are logged with when, where, who and what, with timestamps in UTC.
- Applies when: `AUTHN`, `AUTHZ`, `INPUT`
- ASVS: 16.3.1, 16.3.2, 16.3.3, 16.2.1
- Evidence: spec *Logging* section; test asserting a log entry for a rejected request

### SR-018 No secrets or personal data in logs, URLs or errors
Logs, URLs, query strings and error messages contain no secrets, tokens or personal data.
- Applies when: `LOG`, `DATA`, `SECRET`
- ASVS: 16.2.5, 14.2.1
- Evidence: secrets-pii-logging reviewer clean; gitleaks clean

### SR-019 Data minimisation and inventory
Personal data is collected only when needed and is recorded in the spec with purpose and retention. Image metadata that can identify people or locations (for example EXIF GPS) is removed before storage.
- Applies when: `DATA`, `FILE`
- ASVS: 14.2.4
- Evidence: spec *Data inventory* table; test that stored images carry no GPS metadata

## Secrets and dependencies

### SR-020 No stored secrets; short-lived federated credentials
Nothing secret is committed or stored in CI secrets. Runtime and CI access uses short-lived federated credentials with least privilege.
- Applies when: `SECRET`, `CI`, `IAC`
- ASVS: 13.3.1, 13.3.2
- Evidence: gitleaks clean; workflows use OIDC only; secrets-pii-logging reviewer clean

### SR-021 Trusted, current dependencies
Dependencies, base images and CI tools come from trusted sources, are pinned (version or digest), and have no known exploitable vulnerabilities at merge time.
- Applies when: `DEP`
- ASVS: 15.2.1
- Evidence: OSV-Scanner clean; lockfiles or pins present

## Infrastructure

### SR-022 IAM least privilege
IAM policies name exact resources and actions. Every role carries the lab permissions boundary. Wildcard resources are allowed only for documented unscopable actions.
- Applies when: `IAC`
- ASVS: — (cloud IAM is out of ASVS scope; lab-admin `docs/BASELINE.md` BL-11, BL-12, BL-17)
- Evidence: Checkov or Trivy clean on IAM checks; iac reviewer clean

### SR-023 Private, encrypted storage
Storage is private by default: public access blocked, encrypted at rest (SSE-S3), TLS-only access. Objects reach users only through short-lived signed URLs or an authenticated path.
- Applies when: `IAC`, `FILE`
- ASVS: 12.2.1 (TLS); lab BASELINE BL-19
- Evidence: Checkov or Trivy clean on S3 checks; iac reviewer clean

## CI/CD and AI

### SR-024 Hardened workflows
Workflows run on `pull_request` (never `pull_request_target`), declare minimal `permissions` per job, pass untrusted context through `env` (never inline in `run:`), use allowlisted actions pinned by SHA, and scope OIDC to an environment or a pinned workflow.
- Applies when: `CI`
- ASVS: — (lab BASELINE BL-01, BL-02, BL-20, BL-21)
- Evidence: zizmor and actionlint clean

### SR-025 Untrusted input to AI agents; bounded agency
Content an LLM or agent reads (issues, PRs, comments, documents, files, image metadata) is treated as untrusted data, never as instructions. Agents get only the tools their task needs. Their outputs are validated against a schema before use, and no agent can approve or merge its own work.
- Applies when: `AI`, `CI`
- ASVS: — (OWASP Top 10 for LLM Applications 2025: LLM01 Prompt Injection, LLM06 Excessive Agency)
- Evidence: agent definitions list read-only tools; outputs validated by `gate/security_gate.py`; ruleset forbids self-approval
